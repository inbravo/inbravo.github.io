The 6 Agent Classes

proprietary taxonomy. Elicited in Week 1 before scoring begins. Target class sets the minimum pillar floors for the entire engagement.

Class 1
Query Agent
Answers structured questions about metrics and KPIs in natural language. Stateless or lightly stateful. One question → one answer.
Insurance example
"What was gross written premium for P&C Home in Q3 by distribution channel?"
"Which underwriters exceeded binding authority limits last quarter?"
Min harness: RBAC · audit log · basic output validation
Floors: P1=3, P2=2, P3=2, P4=3, P5=2, P6=2, P7=2, P8=2
Class 2
Research & Synthesis
Aggregates across multiple domains, combines structured data and documents, produces summaries or recommendations.
Insurance example
"Generate a renewal pack for account #AC-7821 including 5-year loss history, exposure summary, market conditions, and rate recommendation."
Min harness: Hallucination detection · source attribution · output validation
Floors: P1=4, P2=3, P3=3, P4=4, P5=3, P6=3, P7=2, P8=3
Class 3
Monitoring & Alert
Runs continuously or on schedule, watches data signals against business thresholds, triggers alerts or downstream actions.
Insurance example
"Alert claims ops when P&C Motor combined ratio exceeds 97% for any regional portfolio for 3 consecutive weeks."
"Notify the chief actuary when IFRS 17 CSM movement deviates >5% from forecast."
Min harness: Circuit breakers · iteration cap · escalation logic
Floors: P1=3, P2=4, P3=2, P4=3, P5=2, P6=2, P7=4, P8=3
Class 4
Workflow Orchestration
Drives multi-step business processes end-to-end, coordinates human review gates and system actions, maintains process state.
Insurance example
"Process a new commercial property application: risk assessment → appetite check → underwriting recommendation → referral if above threshold → bind confirmation."
"Run month-end IFRS 17 close end-to-end with actuary sign-off gate."
Min harness: Full harness · human-in-the-loop gates · step-level audit trail · rollback
Floors: P1=4, P2=4, P3=4, P4=4, P5=4, P6=3, P7=3, P8=4
Class 5
Autonomous Decision
Makes decisions with limited or no human oversight in a pre-approved decision domain. Output triggers direct system action.
Insurance example
"Auto-approve motor claims under £3,000 meeting all standard adjudication criteria — no fraud indicators, PH not on watchlist, damage consistent with reported incident."
"Automatically bind personal lines home renewals within pre-agreed rate change corridor."
Min harness: Full harness · AIUC-1/EU AI Act Art. 9 · explainability · hard-stop controls
Floors: P1=5, P2=5, P3=4, P4=5, P5=5, P6=4, P7=4, P8=5
Class 6
Multi-Agent Orchestrator
Coordinates and delegates to multiple specialist agents (which may be Class 1–5), manages delegation chains, resolves conflicts.
Insurance example
"Solvency II QRT submission orchestrator: delegates to domain agents (P&C, Life, Health), data quality agent, actuarial agent, filing agent — coordinates end-to-end."
"Customer 360 orchestrator across CRM, claims history, risk scoring, and next-best-action agents."
Min harness: Delegation chain accountability · cost envelope at orchestrator level · CSA Agentic Profile
Floors: P1=5, P2=4, P3=5, P4=5, P5=4, P6=4, P7=4, P8=4
03

Week 1 · Target Class Elicitation

Run these 5 questions in the first 30 minutes of the Week 1 Discovery Workshop with the CDO and Business Champion. Document the Target Class Profile before moving to priority question elicitation.

Q1
What tasks or decisions do you want AI agents to handle?
Open-ended. Note what actions the agent takes, not just what insights it produces. "Tell me X" → lean Class 1/2. "Do X automatically" → lean Class 3/4/5. Record verbatim.
Q2
Will the agent's output be consumed by a human making a decision — or will it trigger a downstream system action directly?
Human reads and acts → Class 1/2 candidates. Triggers automated system action → Class 3/4/5 territory.
Q3
Does the agent need to run continuously or on a schedule, without a human initiating each run?
Yes → Class 3 minimum (monitoring) or Class 4/5 (if acting). No → Class 1/2. An underwriting recommendation on demand is Class 2; one that runs nightly against the book is Class 3.
Q4
Does the agent's output domain involve regulated decisions — claims adjudication, underwriting bind decisions, credit scoring, trading, clinical care?
Yes → floor the class at Class 4 minimum. If the agent makes the decision autonomously → Class 5 treatment required. This is the question that changes the readiness bar most dramatically.
Q5
Do you intend to have multiple specialised AI agents coordinated by a higher-level orchestrator?
Yes → include Class 6 in target profile alongside the specialist classes. No → target class is the highest class identified from Q1–Q4.
Insurance worked example · Aegon-type Life & P&C carrier
Q1: "We want agents that monitor our combined ratio in real-time and alert us to deteriorating portfolios, and also agents that can auto-approve low-value motor claims."
Q2: Monitoring → alert to human (Class 3). Claims approval → system action, no human (Class 5).
Q3: Monitoring runs continuously. Claims agent runs on submission event.
Q4: Claims adjudication is a regulated decision → Class 5 treatment confirmed.
Q5: Not in Year 1.
Target Class Profile: Class 3 (Monitoring) + Class 5 (Autonomous Decision). Year 2 may add Class 4 for IFRS 17 close workflow.
Delivery note: This profile immediately sets the readiness bar high. P1=5, P2=5, P4=5, P8=5 are all required for Class 5. Check these pillars first in Week 2 — early signal on whether a Foundation Sprint is needed.

Week 2 · 8-Pillar Scoring Guide

Each pillar: what it measures, insurance-specific interview questions, platform tooling to check, and the 5-level scoring rubric. Score each pillar 1–5 based on evidence gathered. Never self-report — verify claims against platform artefacts.

P1 20% Semantic Asset Coverage ▶

Breadth and quality of formal metric, entity, and KPI definitions in the platform's semantic layer. An agent can only answer questions that are formally defined — undefined terms force improvised SQL with no business-logic guarantee. Insurance focus: combined ratio, loss ratio, GWP, NWP, earned premium, claims frequency/severity, reserve adequacy, binding authority utilisation, IFRS 17 CSM/RA.

Interview Questions
  • Where do your metric definitions live today — BI tool measures, dbt models, or a platform-native semantic layer (Databricks Metric Views / Snowflake Semantic Views)?
  • If an AI agent asked "What is our P&C Motor combined ratio?" — could it get the answer without a human writing SQL for it?
  • How many of your top-20 business questions have a verified, agreed metric definition that any function in the company would accept as authoritative?
  • Are your metric descriptions written for LLMs (natural language, business context) or for data analysts (technical, with SQL references)?
Platform Tooling to Check
Databricks
Unity Catalog Metric Views, dbt Semantic Layer (MetricFlow), AI/BI Genie semantic configuration
Snowflake
Semantic Views (preview), Cortex Analyst YAML semantic file, dbt on Snowflake
Fabric
Power BI semantic models, Direct Lake semantic layer, dbt-fabric adapter

L3 · Developing20–50% coverageFormal definitions in one platform's native layer (dbt metrics, Databricks Metric Views). Column-level descriptions exist but inconsistent. LLM context absent.

P2 17% Data Asset Governance & Trust ▶

Whether gold-layer data assets are documented, owned, quality-certified, and have freshness SLAs — so agents can trust what they consume. An agent acting on stale or uncertified data produces authoritative-sounding wrong answers. Insurance focus: policy data gold tier, claims transactions, premium ledger, reinsurance bordereau, actuarial run-off triangles, IFRS 17 measurement data.

Interview Questions
  • Who is the named data owner for your claims, policy, and premium datasets? Can you name them today without looking it up?
  • Do you have quality monitoring on gold-layer data assets? What happens — who is alerted — when quality drops below threshold?
  • How do you know whether the data an agent would query was loaded this morning or three days ago? Is freshness SLA enforced?
  • Do you have data contracts between producing and consuming teams — or does everyone query source systems directly?

P3 13% Domain & Organisational Alignment ▶

Whether the organisation's domain model is agreed, entities are resolved across domains, and a business champion owns the semantic layer programme. Without this, every function builds its own definitions and the agent gets contradictory answers for the same question. Insurance focus: Customer/policyholder entity resolution (same customer in CRM, policy admin, claims), Counterparty ID for reinsurance, product hierarchy agreed across Finance/Underwriting/Reserving.

Interview Questions
  • Is there a single agreed Customer ID (or Policy ID, Counterparty ID) that every system uses — or do different systems use different identifiers for the same entity?
  • Who is your CDO or business champion for the semantic layer programme? What decisions can they make unilaterally?
  • If the Claims team and Finance disagree on the definition of "paid loss" — who resolves it and how? How long does that take?
  • Do you have a process for publishing new semantic definitions, or does each team build its own in isolation?

P4 18% Agent & AI Consumption Readiness ▶

Whether the semantic layer is configured for machine consumption — API access, LLM-facing descriptions, verified example queries, agent-scoped RBAC. A semantic layer built for human BI users is fundamentally different from one ready for agent consumption. Hard gating rule: P4 = Level 1 caps the overall tier at Foundation regardless of composite score.

Insurance note
Check whether Cortex Analyst YAML semantic file exists for Snowflake; Genie-ready Unity Catalog configuration for Databricks; verified NL→SQL for top-20 insurance questions (combined ratio, loss ratio, GWP, reserve adequacy).

  • Have you tested a natural language to SQL tool against your semantic layer? What percentage of your top-20 questions did it answer correctly?
  • Do AI agent service accounts have separate RBAC from human user accounts — or does the agent use a shared human login?

P7 4% Operational Readiness ▶

Whether the team, tooling, and processes exist to maintain and evolve the semantic layer over time. A semantic layer without operational discipline decays — metrics drift, definitions become stale, coverage shrinks. Especially important for Class 3 (monitoring) agents which depend on freshness SLAs.

Interview Questions
  • Who maintains your semantic layer today? Is it one person or a team? What happens when they leave?
  • Is your semantic layer in version control with a review/approval process for changing a metric definition?
  • How long does it take to add a new metric definition from business request to production availability?
  • Do you have automated tests that run when a semantic layer change is deployed?

P8 10% Agentic Harness Readiness ▶

Whether the platform and team are ready to govern, cost-control, evaluate, and certify agents safely. For Class 4–6 agents, a gap here is as blocking as a gap in P1. Hard gating rule: P8 < Level 3 with a Class 4, 5, or 6 target caps the overall tier at Foundation regardless of composite score.

Insurance note
Class 5 agents (auto-approve claims) require documentation ready for FCA or PRA inspection: AIUC-1 conformance path, EU AI Act Article 9 risk management system, explainability output per claim decision, hard-stop inputs that always require human review (e.g. suspected fraud flags, claims above £X regardless of criteria).
Interview Questions
  • If an agent ran 10,000 queries overnight due to a loop bug — would anything stop it? What is your cost-per-task circuit breaker?
  • Before deploying an agent to production — what is your testing process? Do you have a test suite with deliberate edge cases and seeded defects?
  • When the agent produces a wrong answer — how do you know? What hallucination detection approach do you use for agent outputs?
  • Does the agent use a dedicated service account with scoped permissions — or a shared admin credential?
  • For regulated use cases: do you have documentation ready for a regulator asking "how does this agent make decisions?"

  • Structured for portability to Databricks/Fabric once native support ships
  • Note in delivery agreement: definitions may require spec version update when OSI moves to stable release
90-Day CE Roadmap
3-phase · CDO and delivery team

  • Phase 3 (60–90 days): First agent deployment with eval harness in place
  • Tier 0 customers: Foundation Sprint replaces Phase 1; re-score at end
  • Each phase item maps to: pillar → current score → target score → specific platform action

OSI Export Specification Horizon · 12–18 months

Delivery guidance: Include the OSI Quick Win Spec on Snowflake engagements today (native preview support available). Flag as a 12–18 month roadmap item on Databricks and Fabric engagements — native import is not yet shipped on either platform. This section is a forward reference; keep it in the 90-day roadmap as a Phase 3 item rather than a Week 4 hard deliverable on non-Snowflake customers.

Apache Ossie spec v0.1.1 (Apache Software Foundation incubating project, January 2026). Do not use 0.2.0.dev0 — breaking changes, not backward compatible.

Snowflake
In Preview Two SQL procedures available. Use SYSTEM$CREATE_SEMANTIC_VIEW_FROM_OSSIE_YAML. Known limitation: datatypes not exported; composite primary keys fail cross-tool. Spec locked to v0.1.1.
Databricks
Working group member No native export shipped. Deliver structured JSON following OSI schema conventions. Note in the deliverable: "OSI-structured — natively importable once Databricks ships support (projected H1 2027)."
Microsoft Fabric
Community converter Power BI ↔ Ossie community converter available (not native Fabric). Use the converter for Power BI semantic models. Flag as community tooling, not production Fabric feature.
OSI YAML Structure (v0.1.1)
# Apache Ossie v0.1.1 — Quick Win Spec template (insurance example) semantic_model: name: "insurance_core_metrics" description: "Core P&C insurance metrics for AI agent consumption. the SI CE Assessment Quick Win." datasets: - name: "policy_fact" source: "gold.policy_fact" description: "One row per in-force policy. Refreshed nightly by 06:00 UTC." primary_key: "policy_id" metrics: - name: "combined_ratio" description: "(Incurred losses + LAE + underwriting expenses) / earned premium. Target: below 97% for P&C Motor portfolio." ai_context: "Use this metric to assess underwriting profitability. Values above 100% indicate an unprofitable portfolio. Threshold 97% triggers management review." expression: "(SUM(incurred_loss) + SUM(lae) + SUM(expense)) / NULLIF(SUM(earned_premium), 0)" format: "percentage"

Kill Rules & Foundation Sprint Protocol

These are the conditions under which we explicitly recommend the customer does NOT proceed to T2 Sprint 1 yet. Honest gating at this stage is what builds CDO trust and protects the delivery relationship.

Automatic Foundation Sprint triggers — apply before presenting findings
Kill Rule 1 · Composite score ≤ 29 (Tier 0)
Mandatory Foundation Sprint. Present it positively: "You're in the right place — the gap is specific and addressable. We'd rather give you 6 weeks to fix it than have a sprint fail in month 2." Never proceed to Sprint 1 with a Tier 0 customer.
Kill Rule 2 · P4 (Agent Consumption Readiness) = Level 1
The semantic layer is not machine-accessible at all. Overall tier is hard-capped at Foundation regardless of composite score. Sprint 1 cannot succeed without basic API access and LLM-facing descriptions. Foundation Sprint focus: P4 to Level 2 minimum.
Kill Rule 3 · P8 (Harness Readiness) < Level 3 with Class 4, 5, or 6 target
Tier capped at Foundation for the target class. Proceed to Sprint 1 only for Class 1–3 agents. Explicitly document: "Your target class (Class [X]) cannot be deployed safely until P8 reaches Level 3. This is a prerequisite, not a recommendation." Include a P8 track in the 90-day roadmap.
Kill Rule 4 · 3 or more Class-Gating Gaps for the target class
When three or more pillars are below the target class floor, Sprint 1 is high-risk. Present a Phase 0 gap remediation sprint (2–4 weeks, scoped to close the gaps) before full Sprint 1. This is a judgment call — use it when the gaps are structural (P3, P7) not just incremental (P6).
Sprint Kill Rule — applies during T2 Sprint 1
No qualified pilot conversation within Sprint 1 timeline → retire and redirect
If the customer cannot identify a qualified internal champion for the Sprint 1 pilot by week 3 of Sprint 1, raise the flag immediately. Agreed exit criteria: no named business owner + no agreed pilot scope = Sprint 1 cannot succeed.
Action: Formally retire Sprint 1. Redirect the engagement to T1 (KAM/Sales Velocity track) — help the customer identify and engage the right internal champion before re-qualifying for Sprint 2. Document as a clean exit, not a failure.

Duration & cost
6–8 weeks · $30–40K fixed price
Deliverables
Platform inventory, semantic scaffolding for 5–10 priority metrics, data owner assignment, basic quality monitoring setup, P8 cost controls and agent RBAC configuration
Gate to Sprint 1
P1 ≥ Level 2, P2 ≥ Level 2, P4 ≥ Level 2, P8 ≥ Level 2 (Level 3 if Class 4/5/6 target)

Security & Compliance Industry Standards

OWASP — Open Web Application Security Project
OWASP Top 10 for LLM Applications v2.0 Active · 2025 P8 P2
The foundational security checklist for any LLM-powered system. Ten risk categories, each with prevention controls. The most-cited framework in enterprise AI security procurement. v2.0 (2025) tightened definitions for Prompt Injection (LLM01) and added Vector and Embedding Weaknesses (LLM08) as a standalone risk.
LLM01 · Prompt Injection
Malicious input overrides agent instructions. Direct (user input) and indirect (data the agent reads). Most exploited risk in production agents.
LLM06 · Excessive Agency
Agent granted more permissions, tools, or autonomy than needed. Core P8 control: principle of least privilege for agent service accounts.
LLM09 · Misinformation
Agent outputs that are plausible but factually wrong, used by downstream systems. Addressed by P1 semantic definitions and P8 hallucination detection.
Scoring implication: During P8 Week 2 interview, ask whether the customer has assessed their agent deployment against OWASP LLM Top 10. A yes with documented controls moves P8 toward L4. A no — or "we use prompt guardrails only" — stays at L2/L3.
OWASP Agentic AI Security Project Emerging · 2026 P8 P2 P4
The agent-specific extension to the LLM Top 10. Released mid-2026 to address risks that emerge only when LLMs are given tools, memory, and the ability to take actions autonomously. Critical reading for any team delivering Class 4–6 agents.
Tool Poisoning
Malicious tools injected into the agent's available toolchain — e.g. a rogue MCP server that mimics a legitimate data tool and exfiltrates queries. P8 control: tool registry governance and tool provenance checks.
Agent Hijacking
Indirect prompt injection via data the agent reads — a document, a database record, an email — that contains embedded instructions. Particularly relevant to Class 2 (Research) and Class 4 (Workflow) agents that consume unstructured content.
Memory Manipulation
Poisoning the agent's persistent memory store — e.g. injecting false context into a vector store that the agent retrieves on future runs. P8 control: memory access RBAC and memory integrity checks.
Delegation Chain Gaps
Class 6 orchestrators delegating to sub-agents with no accountability chain — audit trail breaks at the delegation boundary. P8 control: delegation chain logging and cost envelope at orchestrator level.
Uncontrolled Iteration
Agent enters a reasoning or tool-call loop with no circuit breaker — 10,000 API calls, runaway cost, system overload. P8 control: iteration cap and cost circuit breaker mandatory.
Insecure Output Handling
Agent output consumed by downstream systems without sanitisation — SQL injection via LLM-generated queries, script injection in generated content. P4 + P8 joint control.
Scoring implication: For Class 4–6 target class engagements, run through these six risks explicitly in the P8 Week 2 interview. Each unmitigated risk keeps P8 at L2 or below. Document which risks are unaddressed — they become P8 gap items in the CE Maturity Score Report.
OWASP API Security Top 10 Active · 2023 P8 P4
Relevant for Class 4–6 agents that call external APIs — claims systems, policy admin, underwriting platforms, reinsurance portals. Key risks: Broken Object Level Authorization (API1), Unrestricted Resource Consumption (API4), and Broken Function Level Authorization (API5). An agent calling a claims API with an over-permissioned service account violates API1 and LLM06 simultaneously.
Scoring implication: When P4 service account RBAC is being scored, cross-check against OWASP API Top 10 API1/API5. Over-permissioned agent API credentials are a P8 gap regardless of how well the semantic layer is configured.
ISO / IEC Standards
ISO/IEC 42001:2023 — AI Management Systems Active · Dec 2023 P8 P2 P7
The first international standard for AI Management Systems — the ISO 27001 equivalent for AI governance. Specifies requirements for establishing, implementing, maintaining, and continually improving an AI management system. Covers AI risk assessment, impact assessment, documented controls, policy framework, and supplier AI governance. Increasingly required for enterprise AI procurement in the EU and for financial services regulators. Structured around the same Plan-Do-Check-Act model as ISO 27001 — familiar to any organisation with existing ISO certification.
Clause 6 — AI Risk Management
Requires documented AI-specific risk assessment process — maps directly to P8 eval harness and P2 data quality controls.
Clause 8 — AI System Impact Assessment
Mandatory impact assessment before deployment of high-risk AI — aligns with Class 5 deployment gate requirements in our framework.
Annex A — Controls Reference
56 controls across data governance, transparency, human oversight, robustness, and accountability. Strongest overlap with P2, P7, and P8 pillars.
Scoring implication: Ask whether the customer has ISO 42001 certification in scope or is aligned to it. ISO 42001 Annex A alignment moves P8 to L4 minimum and P2 to L3+ minimum. For Class 5 insurance customers, an ISO 42001 gap alongside an AIUC-1 gap should both appear in the CE Maturity Score Report.
ISO/IEC 27090 — AI Cybersecurity In development · expected 2027 P8
The forthcoming cybersecurity extension to ISO 42001, specifically addressing AI-specific attack vectors: adversarial inputs, model extraction, data poisoning, and supply chain compromise in AI pipelines. In balloting as of Nov 2026. Watch for final publication in H1 2027 — once published, it will become the procurement requirement for AI systems in ISO-certified enterprises, replacing ad-hoc security checklists.
Delivery note: Not yet enforceable — do not include in current P8 scoring rubric. Flag to customers pursuing ISO 42001 that 27090 is coming and their AI security controls should be designed to accommodate it. Include it in the 90-day roadmap Phase 3 as a watch item.
ISO/IEC 5338 — AI Lifecycle Processes Active · 2023 P7 P8
Provides processes for AI system development and maintenance across the full lifecycle — requirements, design, verification, deployment, operation, retirement. Complements ISO 42001's management system requirements with engineering-level process controls. Particularly relevant to P7 (Operational Readiness) — whether semantic layer changes follow a governed change management process that can be audited.
Scoring implication: ISO 5338-aligned change management processes for semantic layer updates move P7 to L4. Ask: "Is there a documented process for reviewing and approving semantic definition changes?" If yes with audit trail, P7 ≥ L4.
NIST — National Institute of Standards and Technology
NIST AI RMF 1.0 + Generative AI Profile (NIST AI 600-1) Active · 2023 / 2024 P8 P2 P7
AI RMF 1.0 provides four core functions — Govern, Map, Measure, Manage — for managing AI risk across any system. The companion Generative AI Profile (NIST AI 600-1, July 2024) maps those functions specifically to GenAI risks: hallucination, harmful bias, data provenance, and human oversight gaps. Both are voluntary but widely adopted as the US federal baseline and used by BFSI regulators as a reference point for AI governance expectations.
Govern → P2 + P7
Policies, processes, roles, and responsibilities for AI risk — maps to data governance (P2) and operational process maturity (P7).
Map → P1 + P5
Identifying AI risks in context — maps to semantic coverage completeness (P1) and business context capture (P5).
Measure → P8
Quantifying AI risks with metrics and thresholds — directly maps to P8 eval harness, hallucination detection, and performance monitoring.
Manage → P8
Responding to identified risks — maps to P8 circuit breakers, hard-stop controls, escalation protocols, and incident response.
Scoring implication: NIST AI RMF alignment is the strongest single signal for P8 L4+. Ask: "Have you mapped your AI systems to NIST AI RMF?" If yes with documented Measure/Manage controls, P8 ≥ L4. Reference 600-1 specifically for GenAI hallucination controls.
Threat Intelligence Frameworks
MITRE ATLAS Active · ongoing P8
Adversarial Threat Landscape for AI Systems — the ATT&CK framework for ML/AI. Documents real-world adversarial tactics, techniques, and procedures (TTPs) used against AI systems: model evasion, training data poisoning, model extraction, inference API abuse, and supply chain compromise. Used by red teams and security architects assessing AI deployment risk. Not prescriptive (no controls checklist) but essential context for P8 — understanding what attackers actually do to AI systems shapes what controls to require.
AML.T0051 · LLM Prompt Injection
ATLAS technique for prompt injection against LLM-integrated systems. Documented case studies from production deployments — useful for illustrating agent hijacking risk to a sceptical CDO.
AML.T0018 · Backdoor ML Model
Supply chain compromise via a backdoored model weight file. Relevant for Class 5/6 customers using open-weight models or fine-tuned models from third parties.
AML.T0040 · ML Model Inference API
Abuse of model inference endpoints — rate limits, cost exploitation, data extraction via carefully crafted queries. P8 cost circuit breakers partially mitigate this.
Delivery note: MITRE ATLAS is background reading for the CE Architect — use it to stress-test P8 interview questions, not as a customer-facing checklist. Reference it when a customer asks "what specific threats are you protecting against?"
CSA AI Controls Matrix Active · 2026 P8 P2
Cloud Security Alliance's companion to the Agentic AI Governance Maturity Model — a spreadsheet-format controls matrix mapping AI risks to specific technical and process controls across cloud environments. Covers identity and access management for agents, data residency, model provenance, audit logging, and incident response. Practical complement to NIST AI RMF — where RMF is principles-based, the CSA matrix is controls-based. Particularly useful for customers running agents on multi-cloud estates (Databricks + Snowflake, or Fabric + Databricks).
Scoring implication: If a customer references the CSA AI Controls Matrix in their governance documentation, P8 is at minimum L3. Cross-check which control domains they have implemented — incomplete coverage (e.g. identity controls done, audit logging missing) keeps them at L3 rather than L4.
