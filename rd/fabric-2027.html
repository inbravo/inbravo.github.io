Deep Dive

Fabric IQ Ontology — what it actually is

The Ontology item is a machine-understandable business model stored inside Fabric IQ. Not a data store — a virtual semantic and context layer over existing sources.

Critical distinction: Source data stays where it is (Lakehouse, Eventhouse, Warehouse, semantic model). Ontology holds the definitions and mappings only. No data duplication.
Core Modeling Concepts
  • Entity Type — reusable business concept (Customer, Machine, Shipment)
  • Property — named characteristic with data type + source mapping
  • Relationship — "Customer places Order" — explicit and reusable
  • Metric — governed DAX proxy from source semantic model
  • Rule — natural-language business logic (NL only, not executed)
  • Namespace — domain scoping for large multi-team models
Supported Data Bindings
  • Power BI Semantic Models — DAX stays in source; metrics proxied, not copied
  • Lakehouses, Warehouses, SQL Databases
  • Eventhouses (KQL — real-time + historical)
  • Mirrored Databases
  • OneLake shortcuts, views, materialized views
  • Graph: delta tables from lakehouses/mirrored DBs only — semantic model and KQL sources not supported
Ontology Agent Preview
  • Plan mode (default): discover, draft, validate, query — zero changes applied
  • Act mode: applies proposals after confirmation
  • Attach files as context (10 files max, 5MB each): data dictionaries, business glossaries
  • Queries: DAX (200 rows), KQL/SQL/GQL (1,000 rows)
  • 24-hour conversation limit; 2-day data retention
  • Multi-model: use Act mode to combine multiple semantic models; agent resolves entity conflicts
Governance & Lifecycle
  • Fabric workspace permissions govern access
  • OneLake security + source RLS/OLS/CLS respected
  • Git integration for version control of definitions
  • Deployment pipelines: dev → staging → production
  • Programmatic access + CI/CD support
  • Named version history with restore
New in 2026 Experience
  • Keyless entity types and join-free relationships
  • Type hierarchies and inheritance (single-parent)
  • Shared properties across entity types
  • DAX measures as metrics (proxy, not copy)
  • RDF/Turtle/OWL import-export (Ossie alignment)
  • Calculated columns included in semantic model import
Migration: Old → New Experience

  • Old experience retires Jan 31, 2027

Implementation Guide

Building an Ontology — technical anatomy

Creation flow
  1. Generate Ontology from Power BI semantic model ribbon — requires Read and Build permissions
  2. Fabric creates entity types (tables), properties (columns), relationships, metrics (DAX measures)
  3. Post-generation: bind time-series/real-time data; define entity type keys; add descriptions, synonyms, KV metadata; name relationship types
  4. Add natural-language business rules (e.g. "Frozen product safety stock is 200 units")
  5. Optionally enable Graph for multi-hop traversal (lakehouse delta tables only)
  6. Validate → publish → Git → deploy via pipelines
Metrics: proxy, not copy
  • Ontology stores a link to the source DAX measure, not the expression
  • Edit metric description in ontology: stays in ontology, doesn't change the semantic model
  • Metrics do not auto-update when source DAX changes — manual refresh required
  • "Resolve underlying DAX" requires Write permission on the source semantic model
Rules: governance layer only
  • Natural language only — the ontology does not execute rules against data
  • Retrieved by agents via MCP tool list_ontology_rules
  • Rule metadata: category, region, policyFamily, owner (key-value pairs)
  • Activator integration not available in new experience — configure separately
MCP Server + Foundry IQ
  • Live endpoint: api.fabric.microsoft.com/v1/mcp/dataPlane/workspaces/…/ontologyEndpoint
  • VS Code setup: add to mcp.json; user identity auth (Service Principal not yet supported)
  • Confirmed orchestrators: Claude Sonnet 4.5, GPT-5, GPT-4.1, Gemini 2.5 Pro
  • Foundry IQ: add "Fabric IQ" knowledge source in Azure AI Foundry; requires Azure AI Search with Search Index Data Contributor role
Reference architecture — Lakeshore Retail
  • Lakehouse CSV + Eventhouse KQL + Power BI semantic model bound into one ontology
  • Entities: Store, Product (Frozen Product, Perishable Product), Inventory, Refrigeration Unit, Refrigeration Telemetry, Shipment, Sale, Supplier, Location
  • Query enabled: "Which high-priority stores in the West have frozen products below safety stock, a refrigeration exception, AND on-shelf availability below target?"
  • BFSI analogue: replace refrigeration with LCR threshold, safety stock with minimum liquidity buffer, shipment with collateral position
Known limitations (Oct 2026)
  • Querying parent entity to return inheriting-entity instances: not yet working
  • Business rules not currently considered in agent responses (though MCP-retrievable)
  • Graph does not support semantic model or Eventhouse sources
  • Service Principal auth on MCP Server not yet supported
  • No CMK (Customer-Managed Keys) for Ontology Agent data retention

Open Standards

Apache Ossie — the cross-platform semantic bet

What is Apache Ossie?

  • Open, vendor-neutral spec for exchanging semantic models
  • Datasets, fields, relationships, metrics — JSON/YAML serialisation
  • Entered Apache Incubator July 10, 2026
  • Co-founded by Microsoft and Snowflake
  • Goal: analytics + AI + BI platform interoperability

Microsoft's specific commitments

  • Establish DAX as an Ossie-recognised query language
  • Extend Ossie support for Ontologies (beyond basic semantic models)
  • One Ossie doc → Snowflake Semantic View + Power BI semantic model
  • Semantic Views in OneLake (early look): governed metrics in OneLake, reusable cross-platform

Why this matters for IT Services firms: Ossie breaks the assumption that semantic layer = Power BI only. BFSI clients co-existing on Snowflake and Fabric can define business metrics once and deploy across both. The tooling is nascent and the guidance vacuum is large — early mover advantage is significant.

Engineering Transformation

Syntax to Semantic — The 12-Month Delivery Motion

Engineering teams today use AI at the syntax layer — generating code, tests, and data pipelines faster. The next motion is semantic: encoding domain knowledge as a governed, agent-queryable context layer. This is not a tooling adoption program; it is a capability transformation. The output shifts from code to context — and the accuracy of every agentic outcome depends on how well that context is built.

This motion applies across domains. The speed at which a team can build a credible semantic layer is directly proportional to the depth of domain knowledge already inside the firm.

Prerequisite Before Any Pilot: Domain-Specific Synthetic Data

Customers are not ready to run AI against live regulated or operationally sensitive data. Before any pilot begins, domain-specific synthetic data — built to mirror the schema, statistical properties, and business rules of the customer's real environment — must be in place. Without it there is no safe test environment, no accuracy baseline, and no internal stakeholder confidence before real data is committed. Synthetic data preparation is a gate before the pilot, not a task inside it.

Synthetic data and ontology accelerators are only credible when grounded in real domain knowledge. These are the sectors where that depth already exists and where the motion starts fastest.

13–18 Months: Capability Hardening

Pre-built domain accelerators (BFSI, Healthcare, Manufacturing, Energy & Utilities) reusable across accounts. Retainer model live — monthly ontology governance and agent accuracy management. The firm is positioned not as a Fabric IQ implementer but as the domain-depth play: governed semantic context layers with validated domain knowledge already encoded.

The failure mode to design against

Auto-generating the ontology and skipping the domain SME pairing produces a fast but semantically wrong layer. The result: agents that give confident, incorrect answers on domain-specific questions. The discipline this requires is deliberate domain knowledge encoding — it cannot be automated. An LCR calculation definition, a clinical adverse event rule, a grid outage classification — these require a domain expert to validate. Engineering speed without domain depth is the failure mode.

Industry Shift Analysis

What is actually changing — and for whom

This is not a tooling upgrade. The arrival of Fabric IQ Ontology + agents marks a genuine architectural discontinuity in data engineering. Two things are happening simultaneously: the output of data work is changing, and the primary skill that produces value is changing.

The central thesis: Context Engineering is becoming the new Data Engineering. The team that writes the best ontology definitions, the best agent instructions, and the best business rules will produce better AI answers than the team with more compute or better models. This shift favours IT services firms over hyperscalers — it requires domain expertise and business knowledge, not infrastructure.
Engineering Shift

Syntax Is the New Assembly

Assembly language was once the primary skill of a software engineer. Then compilers automated it — and the engineers who thrived were the ones who moved up to writing C, FORTRAN, and eventually Python. The ones who stayed in assembly became a niche. That same abstraction shift is happening now, one layer higher: LLMs are automating syntax. Python, SQL, PySpark — the languages engineers write today — are becoming what assembly was in 1985. The new engineering craft

ETL as the primary value delivery vehicle. Pipelines were the product. Data engineering meant moving, transforming, and loading data correctly. The pipeline was the deliverable.

🔴

🔴

🟢
Context Engineering as the primary value delivery vehicle. The ontology definition, the agent instructions, the business rules, and the topic libraries are the product. Pipelines become infrastructure.
🟢

🟢
The ontology as L4 in a 5-layer stack. Semantic models become L2 — foundational but not terminal. The ontology sits above them, consuming their metrics and extending their semantics into real-time and entity-relationship domains.
🟢
"Deploy a governed agent" as the data team's output. A Data Agent, Operations Agent, or Copilot integration is the deliverable. The business user gets an interface, not a dashboard.
🟢
Entity-first, business-concept-first design. Architecture starts with what the business calls its objects — Customer, Position, Instrument — and binds data sources to those concepts. The ontology IS the architecture document.
🟢
Semantic metadata as first-class engineering artefacts. Descriptions, synonyms, business rules, and KV annotations are machine-readable and agent-retrievable via MCP. The business glossary is now executable infrastructure.
🟢
AI-assisted ontology discovery. The Ontology Agent in Plan mode explores, maps, and models entities from existing semantic models and data sources. Discovery becomes a conversation, not a weeks-long archaeology project.

Domain Lens

Business domain awareness — the hidden accuracy variable

In the old world, domain knowledge was useful but not causal. A data engineer could build a correct pipeline without deeply understanding what "LCR ratio" or "PD model" meant — the pipeline moved data correctly or it didn't, and technical correctness was the measure. In the agentic world, domain knowledge is directly causal to accuracy. The ontology is only as good as the business concepts it models. The agent is only as accurate as the rules it has been taught. The context is only as useful as the example queries written with real business intent.

The ontology models business concepts — not tables

Generating an ontology from a Power BI semantic model is a mechanical step. Defining it correctly is domain work.

  • You cannot correctly define a Credit Exposure entity type — its relationship to Counterparty, Netting Set, and Collateral, its relevant regulatory metrics — without knowing what those terms mean in a BCBS 239 context
  • A "technically valid" ontology built by someone without domain knowledge will answer the wrong questions accurately — the worst kind of failure because it looks correct
  • The entity type key, relationship directionality, inheritance structure, and metric proxy choices all embed domain assumptions. Wrong assumptions compound across every agent query that consumes the ontology
  • Rule of thumb: the ontology design review should always include a domain SME — a risk officer, treasury analyst, or compliance lead — not just a data architect
Business rules require domain fluency to be agent-useful

Natural-language rules are only as useful to an agent as they are domain-accurate.

  • "LCR exception = ratio below 110% for more than 2 consecutive reporting days" can only be written correctly by someone who knows the regulatory threshold, the calculation basis, and what "exception" means in that firm's specific risk framework
  • A rule written without domain knowledge is worse than no rule — agents will retrieve it, treat it as authoritative, and reason from a false premise
  • This applies equally to HCMI: a rule like "Patient at-risk = length of stay > clinical benchmark for DRG" requires clinical domain knowledge to set the benchmark correctly per diagnostic group
  • Implication: business rules authoring is not a data engineering task — it belongs to a collaboration between the domain expert and the ontology engineer
Context engineering is domain translation

The 6-layer context model for Data Agents is the act of translating deep business knowledge into machine-readable form. The accuracy improvement (+12.1% NL2SQL) comes from this translation quality.

  • Agent instructions require knowing what this agent should and should not answer — a boundary that only a domain expert can draw correctly
  • Example queries must reflect the real vocabulary and intent of the business user — "What is our net open position in EUR rates as of yesterday close?" cannot be written without knowing what NOP means in that trading context
  • Topic libraries (up to 1M chars per SQL source) are only useful if they contain the right business context — regulatory definitions, product taxonomy, organisational hierarchy — all domain artefacts
  • The accuracy gap between a generalist and a domain-aware context engineer is not a skill gap — it is a knowledge gap. The tool is the same; the domain understanding is not
The hybrid profile — the most valuable new hire

The talent implication of domain-as-accuracy-variable is a specific hiring priority that most firms are not yet acting on.

  • The profile: a domain analyst (risk, treasury, trading, clinical operations) who understands data platforms — or a data engineer who has spent 3+ years embedded in a BFSI or HCMI business function
  • This hybrid is rarer and more expensive than either a pure domain SME or a pure data engineer — but one hybrid produces more accurate ontologies than three pure technical engineers
  • For BFSI specifically: former risk analysts, quant researchers, or regulatory reporting leads who have learned Python/SQL are the highest-value profiles for semantic engineering work
  • Sourcing: look inside existing client delivery teams — the most domain-fluent data engineers are already there, doing manual work that the agentic layer will eventually automate. Identify them before they become redundant
  • IT services firms with deep BFSI or HCMI domain knowledge have a structural advantage over hyperscalers and generalist SIs — this is the moat that platform companies cannot replicate with headcount or compute

Databricks Deep Dive

Databricks — the most important competitor to understand

Databricks is the most likely platform you will encounter alongside Fabric in enterprise accounts. Understanding its trajectory is essential for both competitive positioning and identifying co-existence opportunities.

What Databricks is building — the semantic stack
  • Unity Catalog: the semantic foundation — tables, views, functions, ML models, volumes, and metrics all governed under one catalogue. The Databricks equivalent of Fabric's OneLake + Purview + Power BI semantic model combined.
  • AI/BI Genie: conversational NL2SQL interface over Unity Catalog data — users ask questions, Genie generates SQL and returns results. Strong accuracy on well-described Unity Catalog tables.
  • Mosaic AI: the agent runtime — tool calling, RAG pipelines, LLM serving (including external models), Agent Evaluation framework. The Databricks equivalent of Azure AI Foundry.
  • Lakehouse Monitoring: data quality, model drift, and pipeline health monitoring — the Databricks equivalent of Fabric Operations Agent but engineering-focused, not business-goal-focused.
  • Delta Sharing: open protocol for sharing live data across platforms — not a semantic layer standard, but relevant when clients need to share data between Databricks and Fabric.
Where Databricks is genuinely stronger
  • Engineering-grade compute and flexibility: Spark, Delta Lake, MLflow, DLT — unmatched for complex transformations, ML training, and large-scale data engineering. Fabric's engineering layer is improving but not at parity.
  • LLM agnosticism: Databricks serves any model — Llama, Mistral, GPT-4, Claude — with first-class tool calling. Mosaic AI does not favour Microsoft models the way Fabric IQ does.
  • Multi-cloud native: runs on AWS, Azure, and GCP with identical feature parity. Fabric is Azure-only. For clients on AWS or multi-cloud, this is a decisive advantage.
  • Open source credibility: Delta Lake, MLflow, Unity Catalog open source — Databricks is trusted by engineering teams that distrust proprietary lock-in.
  • AI/BI Genie accuracy: Genie performs strongly on well-modelled Unity Catalog tables — competitive with Fabric Data Agent on NL2SQL for structured data scenarios.
Where Fabric IQ wins against Databricks
  • Microsoft 365 integration: Fabric IQ grounds M365 Copilot Chat, Teams notifications (Operations Agent), and Outlook/Word Cowork — Databricks has zero native integration with the Microsoft productivity suite.
  • Business user interfaces: Power BI, Agentic Apps, and Copilot Chat are consumer-grade BI interfaces. Genie is still developer-adjacent — it requires well-structured Unity Catalog tables and technical setup.
  • Real-time + BI unified: Fabric's Eventhouse (KQL) + Power BI semantic model + Ontology in one platform is unique. Databricks requires external Kafka/streaming tooling and a separate BI layer (Tableau, Power BI, or Databricks SQL dashboards).
  • Ontology as a first-class item: Fabric's entity-relationship-rule-metric model with natural language rules and MCP endpoint has no equivalent in Unity Catalog. Unity Catalog has table comments and column descriptions — not an ontology.
  • Governance for regulated industries: Purview DLP, sensitivity labels, Entra Agent ID, compliance with Microsoft's existing enterprise agreements — significantly easier to approve in a BFSI compliance review than Databricks' governance model.
The most common account pattern — co-existence
  • The most common enterprise reality is Databricks for engineering + Fabric for BI and agents — not a winner-takes-all choice.
  • Databricks handles: complex ETL, ML training, feature engineering, large-scale transformations — the data preparation layer.
  • Fabric handles: semantic models, ontology, Data Agents, M365 Copilot integration, business-user-facing intelligence — the consumption layer.
