Genie Ontology — The Context Layer Preview

A live, self-improving knowledge graph of business meaning that grounds Genie agents. Prevents agents from generating syntactically valid SQL that returns the wrong business result.

EXTRACT  →  Ranked snippets from: UC Metrics (highest authority),
             dashboards, SQL history, 50+ app connectors

RANK     →  OntoRank: creator authority × usage breadth
             × dataset linkage × recency

RETRIEVE →  At query time: fetch top-ranked snippets,
             apply UC permission gate, inject into context window

UC Metric Views — Technical Spec GA Apr 2026

YAML-based semantic layer inside Unity Catalog. Define once, query from SQL, BI tools, REST APIs, agents. Advanced features include multi-fact relationships, LOD calculations, parameterised metrics, window measures, measure-on-measure composition.

metric_view:
  name: order_metrics
  source: catalog.schema.orders

  measures:
    - name: total_revenue
      synonyms: ["revenue", "sales", "GMV"]
      aggregate: SUM(order_value)
      filter: WHERE status != 'RETURNED'

    - name: avg_order_value
      aggregate: total_revenue / order_count  # measure-on-measure

  dimensions:
    - name: region
    - name: channel

  materialization:
    enabled: true
    refresh_schedule: "0 6 * * *"
UI vs YAML naming
Catalog Explorer UI calls columns Fields, but YAML syntax uses dimensions. Known inconsistency — worth flagging in implementations.

They don't compete — they're designed to layer. Design intent: define the 20% of concepts that cannot be wrong as Metric Views. Let Genie Ontology handle the long tail (80% of business terms that would never justify a formal YAML definition).

Ontos (Labs) vs UC Business Glossary + Governance Hub

How Context Flows Through the Stack

DEFINITION TIME
  1. Data engineer writes UC Metric View for "revenue" (YAML, versioned)
  2. Domain steward adds Business Glossary definition → linked to Metric View
  3. Genie Ontology extracts: certified Metric View + dashboard tiles + SQL history
     → OntoRank scores certified Metric View highest

QUERY TIME
  4. User asks Genie: "What was our revenue last quarter?"
  5. Genie Ontology retrieves top-ranked snippets → UC permission gate
  6. Snippets injected into context window
  7. Agent generates SQL using certified definition + UC lineage
  8. Result returned with source attribution

Without UC Metric Views, step 7 relies on inferred snippets — which can drift or conflict over time.

Lakewatch — Agentic SIEM GA

Databricks' entry into cybersecurity. Agentic SIEM powered by Claude (Anthropic), built on Unity Catalog + Panther (detection-as-code). Runs entirely on the lakehouse — security data lives where business data already lives.

Uses: Lakeflow ingest (OCSF-aligned) → Delta Lake → UC governance (NIS2/DORA) → Agent Bricks agents for detection, triage, threat hunting → Unity AI Gateway traces as security signals.

SI angle
Competing against Splunk, Microsoft Sentinel, CrowdStrike. Differentiator: no separate security data lake. For regulated industries (BFSI, healthcare) this resonates with data sovereignty requirements.

MemCurrent — Persistent Agent Memory Beta

Three access patterns: Plugins (automatic log/load without agent action), Tools (on-demand explicit query), Dreaming (async consolidation from episodic to distilled). Storage on Lakebase (Postgres) in customer's cloud account — never shared with Databricks.

Security note
Agent memory persists user data across sessions → new attack surface. "Agent memory poisoning" risk: adversarial inputs designed to corrupt future agent behavior. Mitigations: input validation + SHACL shape checks before memory writes.

The Strategic Shift

UC started as a governance layer (control access to tables and files). The 2024–2026 arc is a deliberate expansion into business semantics: making UC the system that knows what things mean.

Traditional data catalogs (Collibra, Alation, Atlan) were built for data stewards — humans who curate metadata. UC's new semantic layers are explicitly designed for AI agents — machines that query business context at inference time. This is a fundamentally different design target.

Layer Highlights

Business Glossary Preview

AI-native design: Genie Code drafts new Glossary pages from query patterns, flags definitions that drift from actual usage, surfaces definitions as context when agents query any linked asset. Key differentiator from Collibra/Alation: the glossary is actively maintained by the platform's AI, not just human stewards.

UC Pages GA

Human-authored markdown context attached to any UC asset. Free-form narrative: "what this dataset is, how to use it, known quirks." UC Pages feed the modeled context side of Genie Ontology — the human voice in the knowledge graph.

Domains GA Oct 8 2026

Business-aligned groupings of UC assets. Agents scoped to a Domain only retrieve context from that domain's assets — bounded, relevant context instead of the whole catalog. Subdomains supported (Finance > Treasury > Liquidity).

UC vs. Standalone Semantic Tools

vs. Traditional Data Catalogs (Collibra, Alation, Atlan)

The no-sync-lag argument
Definitions live inside the same system as the data. No ETL of metadata, no catalog sync job, no "the catalog says X but the table does Y" problem. A Metric View definition is always consistent with the table it reads from.

Collibra/Alation's defense: For enterprises with heterogeneous stacks (Snowflake + Databricks + Oracle + Salesforce), UC only governs the Databricks portion. Catalog Federation is narrowing this gap for some external catalogs.

vs. dbt MetricFlow / Cube

The coexistence reality: Most Databricks customers have dbt. UC Metric Views and dbt MetricFlow are not mutually exclusive — dbt builds and tests the tables; UC Metric Views define business metrics on top of those tables. Apache Ossie (PR #152) is the portability bridge.

The "AgentOS" Framing

"AgentOS" is not an official Databricks product name. It is an industry concept describing the idea that production AI agents need an OS-equivalent: something that handles identity, execution boundaries, memory, permissions, scheduling, and observability.

Databricks framing
"Most teams focus on the core agent loop, but that is only 1% of what it actually takes to run agents in production."

The remaining 99% — deployment, security, context grounding, evaluation, memory, cost control, governance, observability — is what Agent Bricks + Omnigent collectively provide.

Four-Layer Agent Infrastructure Stack

Layer 4 · Skills & Context
Agent Skills (open standard, skill YAML files) · UC MCP Tools · Genie Ontology · MemCurrent (Lakebase)
Layer 3 · Harness (Omnigent)
Meta-orchestrator above any agent CLI/SDK · YAML-declared agent definitions · Policy engine (allow/ask/deny) · Session sharing · Multi-agent composition
Layer 2 · Runtime (Agent Bricks)
DurableAgentServer (sync/stream/background) · Agent Runtime (hosting, identity, scaling) · Runtime Store (Lakebase) · Databricks Sandbox · Agent Bricks CLI + agent.toml
Layer 1 · Platform Primitives
Unity Catalog · Unity AI Gateway · Lakebase · MLflow · Lakehouse//RT + Delta Lake

Key design principle: every agent action is governed by Unity Catalog. A layer-3 policy that denies a git push is enforced before the action reaches the filesystem.

    - pattern: "DROP TABLE *"
      decision: deny         # non-negotiable block

The Policy Engine — The Real Governance Innovation

Traditional guard rails live in the prompt — which can be circumvented by clever multi-step plans. Omnigent intercepts every action before execution:

DecisionBehavior
allowAction proceeds immediately
askSession pauses; notification sent to owner; resumes on approval
denyAction blocked; agent receives a clear refusal and must find another path

Policies defined at three levels: agent YAML, session override, and platform-wide (Unity AI Gateway, workspace admins). This is the mechanism that lets enterprises say "AI at the helm, humans retain control over irreversible actions" — exactly what regulators in BFSI and HLS need.

The "Polly" Multi-Agent Pattern

Polly (orchestrator — plans, delegates, writes NO code)
  ├─ Sub-agent A in git worktree 1 (Claude Code) → implementation
  ├─ Sub-agent B in git worktree 2 (Codex)       → tests
  ├─ Sub-agent C (different vendor than writer)  → code review
  └─ Policy gates applied before any merge/push

Key principles: orchestrator never writes code (avoids context window exhaustion on large tasks) · parallel isolation in git worktrees · cross-vendor review (reviewer uses different model family — correlated blind spots avoided) · spend checks and HITL before final output.

Why These Patterns Now

Every major data platform in 2026 — Databricks, Snowflake, Microsoft Fabric — is building what they each call a "semantic layer." Beneath the marketing, they are converging on the same set of structural design patterns. Naming them gives architects and SIs a vocabulary to evaluate platform maturity, design engagements, and talk to customers without resorting to product brochure language.

These patterns are not product features. They are recurring architectural decisions that appear independently across all three platforms.

The Five Patterns

1
Metric Sovereignty
Business metric definitions exist as first-class governed objects inside the data platform — not buried in BI tools, SQL snippets, or Excel.
▾
The Pattern

The platform is the sovereign of what "revenue" means. Every downstream consumer — dashboards, SQL, agents, APIs — queries the definition from the platform. Sovereignty requires: (1) the definition lives in the platform as a versioned, owned, certifiable object; (2) the platform enforces access to it; (3) business sign-off (certification) is a platform workflow, not a post-it on Confluence.

Cross-Platform Implementations
PlatformImplementationMaturity
DatabricksUC Metric Views — YAML, certification flag, owned by UC principal, open-sourced (UC OSS v0.5)GA Apr 2026
SnowflakeSemantic Views — native schema objects; replaces earlier YAML-in-a-stage approachGA 2026
Microsoft FabricPower BI Semantic Model — DAX measures, hierarchies, roles; anchored in OneLake via Direct LakeGA (mature)
The Gap Before This Pattern

Same metric, five definitions: one in Tableau, one in Power BI, one in the warehouse, one in Python, one in the finance Excel model. Nobody agreed which was correct. Agents trained on all five hallucinated a sixth.

SI Implication
The entry point for every semantic engagement: "Show me your revenue definition. Is it the same in your dashboard, your SQL, and your Genie answer?" If not, Metric Sovereignty is the work to do. Agents built on an unsovereign metric foundation hallucinate with confidence.
2
Behavioral Ontogenesis
The semantic layer grows by observing how the organization uses data — every query and dashboard interaction enriches it. Formal and behavioral semantics blended at query time.
▾
The Pattern

The semantic layer doesn't spring fully-formed from human curation. It develops through behavior — hence ontogenesis, the biological term for an organism developing through its own lifecycle. The formal semantic layer (human-defined) and the behavioral layer (platform-inferred from usage) are maintained in parallel and combined at query time.

The Architectural Insight

Formal-only: misses the emergent vocabulary (e.g., "whale account" that your sales team uses, which nobody put in the glossary). Behavioral-only: no certified ground truth; agents hallucinate on low-confidence inferences. The pattern is always: two layers, one retrieval. The ranking function is the key design challenge.

SI Implication
When agents give inconsistent answers, first diagnostic: "What is your platform's behavioral semantic state?" Databricks customers can audit Genie Ontology for low-OntoRank inferred snippets and replace them with explicit Metric Views or Glossary entries. Recurring tune-up engagement, not a one-time build.
3
Perimeter Isomorphism
The data access boundary and the semantic access boundary are structurally identical — same permission model, same identity provider, same enforcement mechanism.
▾
The Pattern

Isomorphism (from mathematics): same structure expressed differently. Access to the metric definition and access to the underlying data are the same permission check, not two separate gates. If you can't read the underlying table, you can't compute the metric — and you can't see its definition.

Cross-Platform Implementations
PlatformIsomorphism mechanism
DatabricksUC Metric Views are UC objects → inherit RBAC. All MCP calls use on-behalf-of-user OAuth. Strong — one permission model throughout.
SnowflakeSemantic Views are schema-level objects → same RBAC. Caveat: raw SQL tool bypasses semantic view boundary (documented risk — remove raw SQL tool from production agents).
Microsoft FabricPurview sensitivity labels + OLS (object-level security) in semantic model. Dual enforcement, but requires careful configuration.
The Design Tension

Business glossary terms (which don't contain data but describe it) also inherit data permissions — a new employee may not see the definition of a metric they don't yet have access to compute. All three platforms are still working through this.

SI Implication
For any BFSI or HLS agent build: "Does your semantic permission model match your data permission model?" An audit comparing grant structure on UC Metric Views against the underlying tables surfaces misalignments before an agent does. 1–2 week governance engagement with a concrete permission gap report.
4
Concept-Centric Accretion
The platform's organizing unit shifts from technical objects (tables, schemas) to business concepts (Customer, Transaction, Risk Exposure) — which become gravitational centers that all related assets accrete around.
▾
The Pattern

Accretion from astrophysics: a body gains mass by pulling in surrounding matter. Here: the "Customer" concept accumulates all the data, metrics, agents, dashboards, and definitions that relate to it, organized by the platform's catalog. This is not a new idea in enterprise architecture — it echoes domain-driven design (DDD) bounded contexts. What is new is that the data platform natively implements it.

Databricks Domain ≈ DDD Bounded Context · Snowflake Semantic View entity ≈ DDD Aggregate Root · Fabric Business Domain ≈ DDD shared language. SI teams who know DDD can apply it directly to semantic platform design.

SI Implication
Domain design is NOT a technical task — it is organizational and semantic. "Which tables belong to the Customer domain vs. the Order domain?" requires business stakeholder input. A Domain Design Workshop (2–3 days, cross-functional, whiteboard → UC Domains + Glossary seed + Metric View inventory) is a high-margin, high-stickiness engagement that no vendor tooling automates.
5
Open Semantic Covenant
Platforms commit to meaning portability: business logic encoded in their platform will be expressible in open, vendor-neutral formats — and can travel with the data to any tool.
▾
The Pattern

A covenant (not just a contract) implies a mutual, long-term commitment with shared values. Platforms are committing that meaning will not be held hostage. This extends beyond data portability (open table formats) to meaning portability: the business definitions, metric formulas, entity relationships, and domain structures travel with the data.

The three instruments of the covenant: (1) Open table format (Delta/Iceberg — established); (2) Open semantic format (Apache Ossie — in progress 2025–2026); (3) Open catalog standard (Apache Polaris + Ossie YAML stored alongside Iceberg tables — emerging vision).
