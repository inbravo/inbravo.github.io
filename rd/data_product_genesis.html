Legacy Code Dynamism — Where Lineage Quality Is Won or Lost

Generic tools and first-generation AI parsers share one blind spot: they assume code is static. In financial services legacy codebases, it rarely is. The patterns below are a representative sample of the dynamic cases that silently drop lineage edges — making lineage look complete while being wrong. Navigating these is where 12 years of engagement experience becomes the accuracy differentiator.

Phase 1 Detail

Per-Stack Extraction

Each stack has a dedicated extraction strategy. Click each tab for parsing approach, input files, key challenges, and Devin's specific role.

BTEQ / Teradata SQL

Risk: LOW ✓ Proven at GCA Wave 2

Input Files

.sql · .bteq · .ksh (Korn shell scripts with dynamic SQL)

Parsing Strategy

LeapLogic static analysis for table dependencies + LLM column-level extraction for complex transformations. Proven on 11,896 files at 97% accuracy.

Challenges

Teradata-specific syntax (QUALIFY, RANKID, macros); dynamic SQL in KSH string concatenation; macro definitions split across files.

Mitigations

Teradata macro resolver pre-processing pass; flag dynamic SQL as "partial lineage" rather than fail; cross-file macro resolver.

Extraction Flow

Identify SQL statements→ Parse SELECT/INSERT/CTAS→ Expand Teradata macros→ Extract column mappings→ LLM for complex transforms→ Output unified CSV

Informatica PowerCenter XML

Risk: LOW ✓ Most structured format

Input Files

PowerCenter workflow XML files (.xml); .par parameter files for table name resolution.

Key XML Elements

CONNECTOR (explicit field-to-field mappings) · TRANSFORMFIELD (transformation expressions) · SOURCE/TARGET (Teradata table names, direct) · FILTER/LOOKUP (filter and lookup dataset refs).

Challenges

.par parameter files must be resolved; reusable mapplets create cross-XML references; Java/SQL override transforms need LLM extraction.

Mitigations

Parameter resolver (same pattern as .pset); cross-file resolver across mapping XMLs; LLM extraction routed only for Java/SQL override blocks.

Extraction Flow

Export repository → workflow XML→ Resolve .par parameters→ Parse CONNECTOR elements→ Parse TRANSFORMFIELD→ Route overrides to LLM→ Output unified CSV

SAS Programs

Risk: MEDIUM Two-pass required

Input Files

.sas files containing PROC SQL, DATA step code, and SAS macro definitions (%let · %macro · %if · %do).

Three Constructs, Three Strategies

PROC SQL: direct SQL parser (same as BTEQ). DATA Step: assignment parser + LLM for ARRAY loops and MERGE. Macros: must be expanded before extraction.

Pass 1 — Macro Expansion

Resolve all %let and %macro definitions. Substitute macro variables into code. Expand %if / %do conditional blocks. Output: flat, macro-free .sas code per file.

Pass 2 — Lineage Extraction

Parse PROC SQL → column edges. Parse DATA step → assignment expressions. LLM for ARRAY-derived columns. Flag ARRAY columns as "array-generated" in unified CSV.

Ab Initio

Risk: HIGH ⚠ Spike required

5 File Types — None Alone Is Sufficient

.mp — graph plans (data flow topology, source/target tables)
.xfr ★ — transforms (field-to-field DML expressions, the core lineage)
.pset — parameters (table names, env flags, runtime values)
.dml — port schemas (field names and types, reveals passthroughs)
Subgraph .mp — nested calls (recursive traversal required)

7-Step Extraction Playbook

  • Step 1: Parse .pset → parameter resolution map
  • Step 2: Parse .dml → port schema registry
  • Step 3: Recursive .mp traversal (depth-first, cycle detection)
  • Step 4: .xfr DML extraction (rule-based + LLM hybrid)
  • Step 5: Built-in component semantic rules (join/rollup/scan/merge)
  • Step 6: Per-plan lineage assembly
  • Step 7: Cross-stack boundary stitching

DML Parsing Approach — Hybrid (rule-based + LLM)

Rule-based: simple direct assignments out.X = in.Y — covers ~70–80% of cases

LLM-aided: conditionals, lookup functions, date/string transforms — covers residual ~20–30%

Combined accuracy: ~95%+ with human spot-check on a sample. Bootstrap with Ab Initio EME export where available.

Risk Register

Top Risks & Mitigations

All risks are known and mitigated. Risks 1, 2 and 3 have explicit gates — decisions made before engineering commits prevent schedule risk.

HIGH ⚠

Ab Initio XFR Coverage Gaps

Built-in components (Join, Rollup, Scan) have no XFR file — column logic must be inferred from component type + port schema. If coverage is below 60%, column-level lineage is not viable.

Mitigation: 1-week feasibility spike on 5–10 sample plans before committing. Fallback: table-level lineage for Ab Initio, column-level for all other stacks.
HIGH ⚠

Cross-Stack Naming Mismatch

Ab Initio output table names may not match BTEQ source table names after parameter resolution — different teams, different conventions. A single mismatch breaks the stitching edge silently.

Mitigation: Naming convention audit in first sprint using DeepWiki output. Build alias registry for known mismatches before stitching layer.
HIGH ⚠

Barclays Attribute List Not Available

Phase 3 cannot run without the 8–10k report attribute list. If not provided before Phase 3 starts, the MVP cannot demonstrate end-to-end resolution.

Mitigation: Escalate as a named gate dependency. Barclays provides a list of 20–30 priority attributes for MVP before Phase 3 begins.
MEDIUM

AutoSys JIL Export Incomplete

Incomplete JIL export means the active inventory misses live code — Phase 1 processes dead scripts and the graph has incorrect coverage.

Mitigation: Validate JIL coverage against known job counts per LOB. Cross-check with LOB teams before Phase 1 starts.
MEDIUM

Devin Session Cost at Scale

Batch run across 8–10k attributes = thousands of Devin sessions. At Devin's current pricing, this may exceed budget for the full production run.

Mitigation: Use Devin for MVP (20–30 attributes). Full batch uses direct Python pipeline with LLM API calls — same quality, fraction of the cost.
LOW ✓

Target Platform Not Confirmed

Databricks / Snowflake / AWS Native decision is still pending. This could delay catalog publication if outputs are platform-specific.

Mitigation: Simplified SQL is ANSI. ODCS YAML is platform-neutral. Catalog is file-based. MVP delivery is not blocked by platform decision.
