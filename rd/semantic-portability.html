R&D Research · October 2026

Semantic Portability

As every major data platform rushes to build its own semantic layer, customers are trading one form of lock-in for another. The open data era solved storage. The next battle is about who owns the business meaning.

■ Apache Ossie · OSI Standard ■ Databricks · Snowflake · Fabric ■ Legacy Migration · Platform Consolidation

The Problem

Two Layers of Lock-in — Only One Is Being Solved

Apache Iceberg and open catalogs cracked the storage layer wide open. Bidirectional Iceberg access between Snowflake and Microsoft Fabric reached GA in January 2026. But below the data sits an entirely different layer — business meaning — and that one is fragmenting.

Layer 1 — Largely Solved

Storage & Table Format Lock-in

The physical data format: files, partitions, table metadata, and the query catalog. Apache Iceberg provides an open format; REST catalog APIs make it engine-agnostic.

  • Apache Iceberg → universal open table format
  • Apache Polaris → open catalog (Snowflake-donated)
  • Snowflake ↔ Fabric bidirectional Iceberg: GA Jan 2026
  • Supported by: Spark, Flink, Trino, Dremio, DuckDB
  • Remaining risk: engine-specific pipeline features
Layer 2 — Problem Now

Semantic Layer Lock-in

The business meaning layer: metric definitions, dimensions, business rules, data contracts, and governance policies. Each platform writes this in a different proprietary YAML format.

  • Databricks: Unity Catalog metric views (DBR 16.4+, UC-only)
  • Snowflake: Semantic views + Cortex Analyst YAML
  • Fabric: Power BI semantic models (DAX + tabular)
  • dbt: MetricFlow YAML (open-sourced 2026)
  • Same business logic, four incompatible formats

A customer who defines "Net Revenue" inside Databricks Unity Catalog cannot take that definition to Snowflake without rebuilding it from scratch. A customer who leaves Informatica PowerCenter leaves behind not just ETL code but years of embedded business meaning — transformation rules, glossary terms, data lineage — that no migration tool currently carries over.

The Emerging Standard

Apache Ossie — "USB-C for Business Semantics"

The Open Semantic Interchange (OSI) started as a Snowflake-led initiative to define a vendor-neutral YAML format for business metrics. It is an interchange format, not a new semantic layer product. Define once, let any engine read it.

Sept 2025

OSI Launches

Snowflake leads formation. Launch participants: dbt Labs, Salesforce, BlackRock, RelationalAI. Spec work begins under Apache 2.0.

Jan 27, 2026

OSI v1.0 Specification Published

First complete spec covering datasets, metrics, dimensions, relationships, and contexts. Published to GitHub under Apache 2.0. Four reference converters committed: dbt MetricFlow, GoodData, Salesforce, Apache Polaris.

July 2026

OSI Enters Apache Incubator → Renamed Apache Ossie

Project moves to neutral governance under the Apache Software Foundation. Now backed by 60+ organizations. De-facto standard status targeted for 2027.

Aug–Oct 2026

First Native Engine: Dosi

Dosi announced as the first product to execute Apache Ossie YAML to SQL across 15+ warehouse dialects. Cube and Tableau integrations still on roadmap (Tableau: late 2026).

What Ossie Covers

The Spec — Six Semantic Primitives

📦
Datasets

References to underlying tables or views. Platform-agnostic pointer to physical data.

📐
Metrics

Computed business measures (revenue, churn, MAU) with SQL expression logic.

🔵
Dimensions

Attributes for slicing and filtering (region, product, time grain).

🔗
Relationships

Join paths between entities — how datasets relate to each other semantically.

🗂️
Contexts

Named query scopes that bundle a metric set for a specific domain or persona.

🤖
AI Readiness

Machine-readable format that AI agents can query to understand business terminology.

Migration Scenarios

Three Customer Archetypes — Each With a Different Semantic Problem

Scenario A · Legacy Migration

From Legacy to Modern — The Hidden Semantic Debt

Teradata / Oracle → Informatica / DataStage → SAS ⟶ Databricks / Snowflake
What Tooling Handles
  • Lakebridge (Databricks) — Teradata BTEQ, T-SQL, Oracle PL/SQL → Databricks SQL
  • SnowConvert AI — Databricks/Oracle/Teradata → Snowflake
  • MigryX — DataStage, Informatica, SAS conversion with lineage
  • SAS2PY — SAS data steps, macros → PySpark / Databricks
  • LeapLogic — automated ETL migration with LLM-assisted translation
What Nobody Handles — The Gap
  • Business glossary terms embedded in Informatica Axon / EDC
  • Metric definitions in SAS metadata server — what "adjusted revenue" actually means
  • Teradata BTEQ scripts encode business rules that aren't in DDL
  • DataStage transformation annotations — meaning embedded in job descriptions
  • Governance redesign always a separate workstream, always stalls
Scenario B · Modern-to-Modern Migration

Platform Switch — Carrying the Semantic Layer Across

Databricks ⇄ Snowflake ⇄ Microsoft Fabric
What Has Improved
  • SQL migration — both platforms have tooling (Lakebridge, SnowConvert)
  • Data access — Apache Iceberg bidirectional access means data stays put
  • Timeline — full estate: 6–18 months; dual-platform overlap: 3–9 months
  • BI re-pointing — Tableau, Power BI can be redirected to new endpoints
Semantic Layer — Still Manual
  • Databricks Unity Catalog metric views → no export to Snowflake format
  • Snowflake semantic views → no converter to Databricks MEASURE() format
  • Power BI DAX measures → no automated mapping to either platform
  • Apache Ossie would be the solution — but converters for both platforms are still roadmap (Oct 2026)
Scenario C · Platform Consolidation

Running Two Platforms — Semantic Consistency Across Both

Databricks + Snowflake → Single Semantic Layer
Why Customers End Up Here
  • Business acquired a company on a different platform
  • Different business units chose independently
  • Analytics team uses Snowflake, engineering uses Databricks
  • Finance on Fabric, Operations on Databricks
The Ideal State — Not Yet Possible
  • Apache Ossie as the neutral interchange: define "ARR" once in OSI YAML
  • dbt MetricFlow executes it on both engines simultaneously
  • Both platforms read the same definition — no divergence
  • Reality today: manually maintained in two formats, guaranteed to drift

The Invisible Layer

Where Business Meaning Is Trapped in Legacy Platforms

When customers migrate from legacy platforms, migration tools move SQL and pipelines. Nobody moves the meaning. Here's where semantics actually lives in each legacy system.

Teradata
Business Metadata (Viewpoint)
Column descriptions, data classifications, business owner assignments stored in Teradata's proprietary repository. No export tool. Often abandoned at migration.
Oracle
OBIEE / Oracle BI Server RPD
Business model layer (RPD files) contains join logic, metric definitions, hierarchies. Migrating to Fabric/Databricks means rebuilding the entire semantic model from scratch.
Informatica
Axon Business Glossary + EDC
Business terms, stewardship, certification status. EDC REST API exists but no direct export to Unity Catalog, Snowflake Semantic Views, or Ossie format.
IBM DataStage
DataStage Designer Annotations
Business logic is embedded in transformation annotations, stage descriptions, job parameters. Lives in the ETL tool, not in a dedicated semantic layer. Lost when jobs are rewritten.
SAS
SAS Metadata Server + Libraries
SAS libraries map logical names to physical data. Macro variables encode business rules. SAS Visual Analytics has its own semantic layer. All platform-specific, no standard export path.
MicroStrategy
MicroStrategy Schema Objects
Facts, attributes, hierarchies, transformations defined in MicroStrategy's own schema layer. Extremely rich business logic. Zero portability to any modern data platform natively.

Services Partner Angle

How an IT Services Company Should Position on Semantic Portability

Semantic portability is a services-heavy problem. The tooling is either missing, immature, or requires significant configuration. This is a window for any IT services firm with migration, data platform, and governance practice depth.

Migration Practice

Semantic Migration as a Distinct Workstream

Today, migration projects move SQL and pipelines but abandon business meaning. A services partner with automated code migration capability should extend it: extract business semantics from legacy repositories (Informatica Business Glossary, Teradata metadata, SAS libraries) and emit Apache Ossie YAML as a parallel migration deliverable — not a post-migration cleanup item.

Early Adopter Play

Own the Apache Ossie Implementation Playbook

Apache Ossie targets de-facto standard status in 2027. The implementation playbook doesn't exist yet — no reference architecture, no governance model, no migration patterns. The services partner who builds this first becomes the go-to for every enterprise migration that follows, and earns preferred partner status with both Snowflake and Databricks.

Platform Consolidation

Neutral Semantic Governance Layer

For customers running Databricks + Snowflake in parallel, the services play is a neutral semantic orchestration layer — federated metric definitions maintained in dbt MetricFlow or an Ossie-compatible format, compiled to each platform's native dialect. Prevents metric drift while the Ossie ecosystem matures into native platform support.

Regulated Industries

Compliance-Driven Semantic Portability

BCBS 239, IFRS 9, FRTB, and Solvency II all require auditable, platform-agnostic definitions of risk and financial metrics. A bank migrating from Oracle OBIEE to a modern platform cannot lose the certified definitions of "RWA", "PD", or "EAD." This reframes semantic portability as a compliance requirement — a far stronger executive conversation than a data engineering efficiency argument.
